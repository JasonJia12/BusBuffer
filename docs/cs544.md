# How this project uses CS 544

This goes through the system roughly in the order the data moves, from the recorder to the tables the planner reads. For each part I wrote down which idea from the course it uses, why I set it up that way, and what I checked on the real data. The numbers are from my recordings (Oct 8 to Nov 4, 2026) and the checks I ran on them.

## Recorder

The recorder runs outside Docker and only writes files: every changed response from Metro, gzipped, about 110 MB a day. Nothing downstream can lose data, because the files are the source and Kafka can always be filled again from them. I used that a lot. Every time I changed the error logic or the tables, I replayed the recordings through the whole pipeline, for example Oct 8 to Oct 28 at 2000 times real speed, which was 4,418,816 Kafka messages. It also let me measure Metro's feed change (below) on files from before I noticed it.

## Docker Compose

There are four services: one Kafka broker in KRaft mode, Cassandra, a Spark master and one Spark worker. The project folder is mounted at `/project` in both Spark containers, so the driver and the executors see the same code and the same `data/` folder, a bit like a shared file system.

That only works with absolute paths. In my first version the job wrote Parquet to a relative path. The driver ran in `/project`, but the executor's working directory is somewhere else in the worker container, so the files ended up inside the worker container and not in my `data/` folder. Writing to `/project/data/...` fixed it. Even on one laptop, the driver and the executors are separate processes with their own working directories, and the executors are the ones writing the files.

Kafka needs two listeners because it has clients in two networks. Spark runs inside the Compose network and reaches the broker as `kafka:19092`. The producer runs on the laptop and uses `localhost:9092`. A Kafka client only uses the address it was given for the first request. After that it connects to the address the broker advertises, so each listener has to advertise an address that works from where its clients are. If the broker only advertised `localhost:9092`, Spark would try to connect to its own container.

Kafka and Cassandra keep their data in named volumes, so `docker compose down` keeps the topic and the tables. Before I added the Kafka volume, `down` deleted the topic.

## Kafka

Each message is one trip in one poll, with its list of stops and predicted arrivals. The busiest poll (7:24 am on Oct 8) had 265 trips and about 6,700 stop predictions. One message for the whole response would give one big message with nothing to partition by. One message per stop would be about 6,700 messages a poll, and Spark would have to put each trip back together. The error logic keeps its state per trip, so a trip is the natural message. The largest message is 5.5 KB, a busy poll is about 400 KB, and gzip in the producer makes them about 7 times smaller.

The key is the trip_id and the topic has 4 partitions. The producer picks the partition from a hash of the key modulo 4, so all polls of a trip go to the same partition, and Kafka only keeps messages in order inside a partition. The error job needs each trip's polls in time order. If a later poll came first, the stops missing from it would count as passed and get wrong actual times. Within a micro-batch the job sorts a trip's polls by feed time itself, but across batches it relies on Kafka's order. I checked it on a replay of Oct 9 7:24 to 7:27: 1,412 messages went to the 4 partitions (316, 410, 372 and 314), and reading them back, every one of the 239 trips stayed in one partition with its polls in time order. Because the partition comes from the hash modulo 4, the topic also has to keep 4 partitions. With 5, most trips would hash to another partition, and a running trip's newer polls would no longer be in order after its older ones.

The producer client also has to keep the order and not lose polls. kafka-python 3 does both by default, so I didn't set anything: it waits until all in-sync replicas have a message (acks=all, which with one broker is just that broker) and retries failed sends. A retry could put a message behind a later one, but the producer is idempotent by default: it numbers its batches for each partition, and the broker rejects a batch that arrives out of order or twice.

Kafka keeps the order things are sent in, not feed time, so the rest is up to how I run the producer. After the producer has been stopped, I first replay from the last file it sent up to now, and only then switch to live. For the same reason I never filled in Oct 28 3:00 to 3:46. Those messages would have come after the live test messages from 3:5x, out of order for the trips in both.

Two jobs read the topic and neither knows about the other. The error job starts from the earliest offset, because it needs everything in the topic, and the live job from the latest, because it only needs what the buses are doing now. That setting only counts the first time, when the checkpoint is empty. After that each job goes on from the offsets in its own checkpoint. Spark keeps the offsets itself instead of committing them for a consumer group, so I could stop and restart one job while the other kept running.

## Stateful streaming

For each stop, the error job keeps the first prediction made in each minutes-ahead range (1, 2, 3, 5, 7, 10, 15, 20 and 30 minutes). When the stop drops off the front of the trip's list, it outputs actual minus predicted for each of them. This needs memory across polls for each trip, so the job groups by trip_id and uses `applyInPandasWithState`. Spark sends each trip's rows from the JVM to a Python worker as Arrow batches, which is why the Spark image has pandas and pyarrow. The state has to fit a Spark schema, so it is the trip's Python dict, pickled into one binary column.

The logic itself is a plain function, `update_trip` in `busbuffer/prediction_errors.py`, with 6 unit tests on small hand-made polls. The Spark code only parses the JSON, explodes the stops, groups by trip, sorts the polls and calls the function. Because the logic is the same function either way, I could compare the stream with a simple loop over the files. On the replay of Oct 8 to Oct 28, Cassandra, the lake and the loop agreed on all 6,927,098 errors, in all 9 minutes-ahead ranges and in the counts for each of the 20 service dates.

The event time is the feed's header timestamp, with a 10-minute watermark and an event-time timeout of 1 hour after a trip's last poll. The watermark is the newest event time Spark has seen minus 10 minutes, so it moves with the data, not with the clock. A trip is removed from the state once the watermark passes its timeout, about 70 minutes of feed time after its last poll, so a replay at 2000 times real speed doesn't keep every trip for 70 real minutes. At most about 1,300 trips were in the state at once, and the watermark never dropped a poll, because the producer sends them in order.

Spark only moves the watermark and checks timeouts between batches, and it hands the function all of a trip's polls in a batch at once. After the restart on Nov 2, batch 1038 covered Nov 1 6:19 am to Nov 2 6:56 am, so the same trip_id from two days could come in one call. That's why `update_trip` checks for the 1-hour gap itself, and the Spark timeout only keeps the state small.

groupBy sends each trip to one of the shuffle partitions by hashing trip_id and route_id. The default of 200 shuffle partitions would mean 200 tasks a batch for a few hundred trips, so I set it to 4. For a stateful job that number is fixed once it starts: the state is stored per shuffle partition (`state/0/0` to `state/0/3` in the checkpoint), and the offsets files save `"spark.sql.shuffle.partitions":"4"`, which Spark uses again on a restart whatever the config says. The trigger is 1 minute, so a live batch has about two polls.

## Restarting without duplicates

Spark writes a micro-batch's offsets to the checkpoint's `offsets` folder before running it and a file to `commits` after it, and the state gets a new version for every batch. If the driver dies in between, the restart runs the same batch again, with the same offsets and the state from before it. So a batch can be written twice, which is at-least-once, and both outputs have to give the same result when repeated. Each batch goes to its own Parquet folder, `batch_id=N`, which is overwritten when the batch runs again. In Cassandra a write with the same primary key replaces the row, and the key (route, service date, minutes ahead, predicted_at, trip, stop) is one error.

I tested this by killing the driver with `kill -9` in the middle of batch 179, after its offsets were logged and before the commit. After the restart, the output for 6 am to 2 pm was still identical: 233,752 errors, none lost or duplicated. I did the same with the Cassandra write added, killing it during batch 10, and the output was again identical.

There were real restarts too. On Oct 31 I stopped everything to free memory, and on Nov 2 the job resumed from batch 1036 with the new gap rule in `update_trip`. That worked because Spark only sees the state as one binary column, so changing what's in the dict doesn't break the checkpoint. On Nov 3, recreating the Cassandra container made a write fail and the job stopped. I restarted it from its checkpoint at batch 1518.

## Cassandra

The planner asks two questions about live data: which trips are coming to my stop, and when that trip gets to my destination. CQL has no joins, so the live job writes the same predictions to two tables, partitioned for each question. `live_predictions_by_stop` is partitioned by stop_id. `live_predictions_by_trip` is partitioned by service date and trip_id, because trip ids repeat every day. Each question reads one partition. On real live data on Oct 28, all 187 trips of the newest poll in `live_predictions_by_trip` matched the recorded file exactly.

The predicted arrival changes every poll. If it were part of the primary key, every poll would add a new row and the old ones would stay. So the key only has things that stay the same, the trip and the stop_sequence, and the times are normal columns that each poll overwrites. The real data broke my first key for `live_predictions_by_stop`, which was `((stop_id), trip_id)`. 96 route 81 trips pass the same stop twice, so the two arrivals overwrote each other. Adding stop_sequence to the key fixed it.

Both jobs write to Cassandra through the Spark Cassandra connector, so each executor writes its own rows, instead of collecting them to the driver and inserting them one at a time. Cassandra decides which write is newer by its write timestamp, not by feed time. If one batch had two polls of a trip, which one stayed would depend on the order the writes happened to run in. So the live job first keeps only the newest poll for each trip and stop_sequence in the batch, with `row_number` over a window.

Both live tables have a 2-hour TTL, so old predictions clean themselves up. But Cassandra never changes its data files, so an expired row can't just be removed. It turns into a tombstone, which stays until compaction after `gc_grace_seconds` (10 days by default). A `count(*)` over a whole live table failed with READ_TOO_MANY_TOMBSTONES after scanning more than 100,000 tombstones. Reading one stop's partition still takes a few milliseconds, so the TTL tables work because the planner only ever reads single partitions. The planner also only uses the rows from a trip's newest poll, since a stop the bus has passed keeps its last row until the TTL removes it.

`prediction_errors` is partitioned by route and service date. I measured it after the full replay: 476 partitions, 14,553 rows on average and 86,166 at most, so I didn't need to add the hour. A partition by route alone would keep growing forever.

`error_quantiles` is partitioned by the group (route, direction, day type, hour) and clustered by minutes ahead. Wider groups use 'all' and -1 in the key, so all four group sizes fit in one table, and the planner reads at most four small partitions.

The service date is in two partition keys, so getting it wrong puts rows in the wrong partition. The feed has no start date, and there is no quiet time at night to split on: the timetable runs from 4:37 to 27:16, and some night polls already list the next day's trips up to about 20 hours ahead. Predicted time minus the trip's scheduled start (seconds after midnight, from `stop_times.txt`) is close to midnight of the service day, off only by how far into the trip the stop is and how early or late the bus is. I add 12 hours and take the date, so an early or late bus or the daylight saving change can't push it into another day. It has 3 unit tests.

## Batch job and calibration

The streaming jobs produce facts, and a batch Spark SQL job turns them into what the planner uses. `error_quantiles.py` reads the Parquet lake, joins the direction from `trips.txt`, keeps the errors from before the feed change, and computes the 5% to 95% quantiles with `percentile_approx`, plus the count. `explain()` shows the join with the 14,199 trips planned as a sort merge join: Spark can't estimate the size of a table made from a Python list, so it plans to shuffle both sides by trip_id. Adaptive query execution changes it to a broadcast hash join when it runs and sees that the trips are small, but by then the lake rows have already been shuffled. GROUPING SETS gives all four group sizes in one query instead of four. The first run took 44 s and wrote 12,189 rows. The containers run in UTC, so I set the session time zone to America/Chicago in the builder, or `hour()` would have been 5 or 6 hours off.

`percentile_approx` is fine for the planner: with the default accuracy of 10,000, the rank of the value it returns is off by at most n/10,000, which for all routes at 10 minutes is 49 out of 490,791 errors. For the error numbers by minutes ahead in the README I used the exact `percentile` in `analysis/route_80.py`.

In live mode the error job writes a folder every minute. By now the lake has 3,910 batch folders and 9,212 Parquet files for 176 MB, about 19 KB per file. The `batch_id` folders are there so a retried batch can overwrite its own output, not to make reads faster. The batch jobs filter on dates, which aren't folders, so they read every file. That's fine at this size, but a longer run would need the small files compacted.

To check the planner's confidence I split by time, not at random. For each day from Oct 11 to Oct 20, `analysis/calibration.py` builds the quantiles from the earlier days only and counts how many of that day's errors fall below each quantile. The errors are cached, so only the first of the ten quantile queries reads and joins the lake. The held-out errors then go through the driver with `toLocalIterator`, which brings one partition at a time instead of everything like `collect`, so each one gets its group from the planner's own `pick_quantiles`. A join in Spark would be faster, but it would check a copy of the fallback rule instead of the planner.

Over 3,224,951 errors, 10.3% were below the 10% quantile, so being at the stop by the 90% time would have caught the bus 89.7% of the time, and between 88.1% and 90.6% on each day. Errors on the same trip and day are related, so the day-to-day range is a better measure of the spread than the 3.2 million count.

## Cores and memory

In a Spark standalone cluster an app takes all the worker's cores by default, and a streaming app never finishes. When I tried to start a second app while the error job ran, it got no executors and just waited. Setting `spark.cores.max` to 4 for the error job and 2 for the live job fixed it.

Memory was the other limit. By default Cassandra took a 4 GB heap, half of Docker's memory, so I set `MAX_HEAP_SIZE` to 1G. Even then, both jobs, Cassandra and Kafka used about 6.9 GB of the 7.7 GB Docker had while idle, and a replay with both jobs running got Cassandra killed for running out of memory. So I ran backfills with the error job only, and raised Docker to 10 GB before running both jobs live.

## Metro's feed change

On Oct 20 at 13:20, Metro started sending 19-55% of the responses each day from a second source. Those responses are about a minute old and don't mark detours. I found it because the GPS check drifted: GPS minus my actual time, 7-10 am, had a median of +1 s on Oct 9 but -24 s on Oct 22. I fixed it in the producer, so both jobs get the fix at once: it skips responses with no trip_modifications entities. The full responses left can be more than 2 minutes apart, so I also changed `update_trip` to keep a trip's saved predictions over a long gap instead of starting the trip over. The results only use data from before the change.

## What I didn't get to

Everything runs as a single node: one Kafka broker, one Spark worker and one Cassandra node with replication factor 1. So I never showed replication, consistency levels or a node going down, only the driver restart. With three Cassandra nodes and replication factor 3, writing and reading at QUORUM (2 of 3) would give R + W > RF, so every read would overlap the latest write, and one node could be down. The lake is a local folder shared through a Docker mount, not HDFS.
